# GeoBlock map and terrain resource survey

Checked 4 October 2026. This is a source catalogue for the scene-builder design, not a claim that every source is already wired into the ComfyUI prototype. The product-facing landmark search accepts user-chosen places; separate example graphs retain prepared Worm's Head and Woodside Library scenes. “Resolution” below means grid spacing or imagery pixel size, not guaranteed geometric accuracy.

## Building shape is a separate quality gate

The [Open 3D City Model Catalog](https://catalog.open3d.city/) is now the discovery entry point for city models. It is a community-curated, machine-readable STAC registry with region, format, LoD and city-object metadata. Its own beta notice says datasets can be incomplete and licence data inaccurate. The [city3d STAC extension](https://github.com/cityjson/stac-city3d) reports which LoDs and object types occur in an item; it does **not** certify that every building in a city or every building visible to a camera is modelled. A dataset footprint is an availability lead, not proof of feature completeness.

The prototype's **Discover Geometry Sources** node lists a short curated set alphabetically under Catalogs, 3D city models and Landform terrain, with a place/region search. It includes only sources that advertise measured landform relief or actual 3D building geometry, plus the catalog as a discovery service. This is source-family filtering: only the prepared Worm's Head landform is currently shot-ready. Hamburg, Helsinki and 3DBAG remain candidates until their exact target and visible corridor pass the geometry checks below. Woodside is absent from the eligible browser because its current control is height-extruded footprints, not roof shape.

### Renderer lead: forge3d

The [forge3d 1.41.0 announcement](https://x.com/milos_gis/status/2106764377735016932) and [SPLAT-FUSED documentation](https://github.com/milos-agathon/forge3d/blob/main/docs/splat-fused.md) describe a Python/Rust renderer that combines georeferenced Gaussian-splat PLY, COPC LiDAR and DEM terrain with shared shadows. Its `render_fused_sequence` API reuses scene data across camera views, which could generate programmatic reference frames for a flyover. This is a **rendering/tool candidate, not a geometry dataset**: it does not create missing building or landmark shapes. The documented fused call accepts splats, point cloud and terrain, not CityGML/OBJ meshes; the separate building-import pipelines are described as Pro features in the [project README](https://github.com/milos-agathon/forge3d). The main-branch changelog describes 1.41.0, but GitHub Releases and PyPI still listed 1.40.1 when checked on 4 October 2026. Test the published wheel after 1.41.0 appears, using licensed local splats plus measured terrain before considering it for a demo.

**Worm's Head renderer trial, 4 October 2026:** The published forge3d 1.40.1 Linux wheel loaded on the RTX 4090/Vulkan. [The trial script](../scripts/try_forge3d_worms_head.py) reused the measured Welsh LiDAR DTM and sampled the saved Blender camera route at frames 1, 144, 216 and 288. Its `MapScene` offscreen renderer produced four 640×360 checkpoint images in about 3–4 seconds each; see `outputs/B_lidar_full_2m/forge3d_probe/manifest.json`. This is a working renderer proof, **not yet an eligible H3 blocking control**. Only 9.6% of the 5 km raster is measured land; filling no-data cells to stage sea made a finite bright-blue sheet and fragmented the coastline and cliff edges. At frame 144 the nearby land drops out of view although it is present in the Blender control. A direct viewer snapshot also returned black for both the terrain GLB and a test cube on this machine, while offscreen `MapScene` rendered successfully. Keep Blender for the current Worm's Head motion guide. A future forge3d trial needs a separate, larger sea surface plus land-mask-preserving terrain geometry and camera parity before a full clip or H3 comparison.

The Woodside LiDAR test estimates one height per accepted OSM footprint and extrudes it to a flat-roof block. This establishes depth, **not the building's roof or façade geometry**. Its current height gate must not be described as a building-shape gate.

San Mateo County also publishes a [building-footprint layer with elevation and height fields](https://gis.smcgov.org/maps/rest/services/Common/SanMateoCounty_Basemap/MapServer/29) and [downloadable footprint files](https://www.smcgov.org/tsd/gis-data-download). Those are useful inputs, but the published layer is polygon geometry, not a roof-surface mesh. A search of the county's open catalogue found no ready-made Woodside LoD2 model; that is an absence of a verified source, not proof that no private or unpublished model exists.

For an architecture-led shot, require a 3D building mesh with roof planes or a validated LoD2 reconstruction covering the target and the visible camera area. The availability check must inspect the actual tile and target building, not just a provider's regional coverage. Footprints, height attributes, LoD1 extrusions, and aerial drapes do not qualify as measured building shapes. Natural-landform shots continue to use the separate measured-relief rule.

### Photogrammetry extraction projects checked 4 October 2026

The [retroplasma Apple Flyover](https://github.com/retroplasma/flyover-reverse-engineering) and [Google Earth](https://github.com/retroplasma/earth-reverse-engineering) repositories both export textured 3D map tiles in their historical implementations, but both were archived in August 2022. Apple requires an undocumented manifest/authentication path and the old code targeted Go 1.15; the Google OBJ exporter was tested on Node 8 and uses undocumented `kh.google.com` resources. No current end-to-end export was verified. A [recent independent report](https://news.ycombinator.com/item?id=49427963) says Apple's tile delivery and HEIF textures have changed; treat this as a compatibility warning, not a confirmed test of every location. These meshes also combine roofs, trees and terrain rather than providing individually attributed building objects.

For GeoBlock's reusable Blender/H3 references, the source rights matter separately from whether an exporter still runs. [Apple Maps terms](https://www.apple.com/legal/internet-services/maps/terms-en.html) restrict extracting/reusing service content, and [Google Maps Platform terms](https://cloud.google.com/maps-platform/terms) restrict exporting content outside its services. Open-source exporter code does not grant a licence to the extracted map data. Human viewing for composition or checking independently sourced geometry is a different workflow from importing an extracted mesh into Blender, rendering it as a control, or tracing its geometry into a new mesh. The maintained, open-data route is [3DBAG's building/tile API](https://docs.3dbag.nl/en/delivery/webservices/), published CityGML/CityJSON, and an importer such as the [Blender CityGML add-on](https://github.com/virtualcitySYSTEMS/blender-citygml-importer-exporter); those are candidates for the next prototype rather than installed GeoBlock providers.

The [March 2026 Google Earth-to-FBX video](https://www.youtube.com/watch?v=dPNCxKceOe4) demonstrates the third-party “Google Earth Map 3D Exporter” (`Earth2MsfsWPF.exe`): search/select a London building, choose maximum LOD, download GLTF tiles/textures, import the GLTFs into Blender 5.1, relink missing PNG textures, join meshes, and export FBX with embedded textures. The [tool listing](https://freedom3d.art/post-category/category-app-software/google-earth-map-3d-exporter/) describes extracting Google's buildings, streets and terrain. This shows a manual conversion path, not an official Google export or a validated source for GeoBlock. It does not demonstrate a stable programmatic interface, georeferencing/metric accuracy, separate building semantics, or rights to reuse the extracted mesh. Keep as a technical reference only; do not promote it into the eligible dataset catalog without resolving those issues.

## Recommended Worm's Head stack

1. **Land:** Welsh 1 m DTM where valid. Keep gaps explicit. Use GEDTM30 only for broader land context or carefully identified missing patches. A 30 m grid cannot reconstruct the narrow tidal causeway or recover a cliff edge absent from the LiDAR.
2. **Sea floor:** Inspect EMODnet source and quality layers at the site. Use its MSL export only after the land and marine heights can be transformed into the same verified vertical reference. Use GEBCO for distant ocean context, not shoreline detail.
3. **Appearance and features:** Add Sentinel-2 colour and WorldCover material classes at their native detail, then OSM paths/coastline as optional vector overlays. Keep the licensed Commons photographs for H3 reference and visual checking rather than projecting them onto the mesh.
4. **Sea surface:** Set a separately chosen water height and tide state; the instantaneous sea is not the zero value of a terrain model. For a physically anchored shot, obtain a nearby tide observation or prediction and its datum conversion. For a clay study, keep the chosen water height explicitly labelled illustrative.

This ordering lets multiple maps contribute to *one scene* without averaging incompatible surfaces. Land DTM, DSM detail, bathymetry, imagery, vectors and sea level should remain separate, inspectable layers. The source map should record which dataset supplied every elevation cell.

## Proposed source-picker flow

```text
Place + area + shot
    → Discover intersecting resources
    → Coverage preview: land / sea / gaps + native spacing + survey date
    → Source Plan (Auto / Pinned / Composite)
         land DTM: Welsh LiDAR 1 m
         land fallback: GEDTM30 30 m [optional]
         surface detail: Welsh DSM or USGS LPC [required for any building shot]
         roof-shape mesh: LoD2 / validated reconstruction [required for architecture-led shot]
         seabed: EMODnet 2024 [optional]
         appearance: Sentinel-2 + WorldCover [optional]
         features: OSM [optional]
    → Align horizontal CRS and verified height datums
    → Inspect overlap residuals and provenance mask
    → Build scene + source report
    → Plan shot → Build H3 references
```

Each picker row should show: source type (DTM/DSM/bathymetry/imagery/vector), AOI coverage percentage, native cell size, acquisition date, licence, API/key requirement, vertical reference and status. “Auto” chooses the best compatible land DTM per cell; “Pinned” uses only the chosen source and displays gaps; “Composite” lets the user choose a base plus named fallbacks. The graph should expose a preview of coloured source footprints and a final provenance/attribution report before any expensive render. Never change datasets silently between reruns.

### Fusion gates

- Reproject rasters and vectors to one local metric coordinate frame. Transform all **elevations** to a declared common vertical frame with documented grids; EPSG:27700 alone says nothing about height. The existing Welsh crop cannot pass this production gate until its height datum is confirmed ([local check](source-check.md)).
- Treat nodata as unknown, including water-masked cells. Do not fill sea with land terrain, invent an intertidal crossing, or upsample 30 m data and call it 1 m detail.
- Compare aligned datasets in stable, bare-ground overlap. Record signed residuals and allow seam blending only where both source classes and dates make sense; retain a source-ID mask and an uncertainty/quality flag. Never average a DTM with a DSM.
- Keep bathymetry and the land mesh separate near shore unless their height references and overlap support a defensible join. EMODnet LAT, EMODnet modelled MSL, GEBCO's assumed MSL, EGM2008 and ODN are **not interchangeable labels**.
- Every 3D blocking shot needs measured height at its target. A DTM can qualify for a natural landform only when the landmark itself has sampled elevation and local relief. A building shot needs an intersecting DSM or point cloud with validated ground alignment, measured height for the target building, and enough reliable neighboring roof coverage. DTM-only, imagery-only and footprint-only candidates are never eligible for building blocking. The Woodside gate requires the target building and at least 70% of nearby mapped buildings to pass; rejected footprints are omitted rather than assigned guessed heights.
- For a shot whose subject is a building or landmark architecture, also require roof-plane/mesh geometry for the target and visible neighbors. The current Woodside scene has **not** passed this stronger test; it remains a height-and-footprint prototype. A source marked LoD2 is only a candidate until its specific building is checked for missing/simplified geometry, date, licence, and alignment with the terrain.
- Emit a manifest with source IDs, source URLs, selected tiles, licences, download/checksum information, acquisition dates, transforms, coverage fractions and every user override. Exported renders should retain attributions.

## Implementation order

1. **Discover Sources** now lists a curated alphabetical source index and filters by text/category without downloading data. Next, ingest the Open 3D City Model Catalog's linked STAC Collections/Items and check the requested area against their footprints and source availability APIs. Treat imported entries as candidates until verified.
2. Add a **Choose Sources** node with separate slots for land, optional fallback, bathymetry and appearance. Initially allow the two already-read land datasets at Worm's Head; keep unsupported choices visible as “not installed”.
3. Add **Preview Coverage** and a composite compiler only after a validated datum conversion and per-cell provenance mask are in place. For the first comparison, A/B sources are more informative than a blended mesh.
4. Extend automatic source discovery by region (Welsh and English LiDAR, then global DTM/DSM), followed by imagery, coastlines and bathymetry.

The most useful immediate test is a side-by-side 1 m LiDAR versus 30 m GEDTM30 preview over the *same* Worm's Head footprint, with gaps and sources coloured. It will reveal what a user gains or loses by switching models before we make composites automatic.
